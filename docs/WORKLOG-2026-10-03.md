## Payments — Revolut, and a claim I got wrong

Square was chosen, then superseded the same day by Revolut Merchant (`8a7444f`).

**I asserted Revolut "is not a subscriptions engine" and recommended keeping Stripe for the OS
subscription. That was wrong** — Leo challenged it and Revolut shipped a native Subscriptions
API in January 2026: plans → variations → phases, each phase carrying an amount in minor units
and a `cycle_duration` as an ISO-8601 duration, with automatic charging, retries for failed
payments, saved payment methods and webhook events. **Multi-phase variations are how free
trials are expressed**, which is what the OS pricing page already promises. Corrected in
`b8bcd97`, with the false premise left visible rather than quietly edited, because it had
changed a recommendation.

What survives is a *migration* question, not a capability one: live tenants carry Stripe ids
and card mandates, and **a mandate does not transfer between processors**. Revised
recommendation — new subscriptions on Revolut, existing Stripe tenants stay until a migration
is decided. U4 is no longer blocked.

## Theme switcher — five palettes plus a custom accent

A control in the nav on all 12 pages: five preset themes (Trade, Ink, Harbour, Bone, Grove)
and a colour wheel.

**The interesting problem is the wheel.** A visitor can pick `#ffeaea`, and a link in that
colour on white is about 1.05:1 — invisible. So the pick is used *exactly* for what it is good
at (fills, large display type, icons) and a derived, contrast-checked shade is used for links
and small text. That is the existing `--accent` / `--accent-strong` split, computed instead of
hand-picked. The derived tokens are what get persisted, so a tiny inline `<head>` script can
reapply them before first paint without duplicating any logic — a deferred script would flash
the default palette on every navigation, which reads as a broken toggle.

Three things this forced, all of them correct:

- **`--fg-on-accent` became load-bearing.** A dark theme needs *ink* on a light accent, not
  white. Five rules hardcoded `#fff` and would have produced an invisible button label on the
  dark theme; they are now inverse pairs or the token.
- **`tests/tokens.test.mjs` runs the full contrast battery against every theme**, not just the
  default, and fails the build if any one drops under AA. A theme switcher is otherwise a way
  to ship a palette nobody checked.
- **The dark theme is not the light theme inverted** — it has its own band, shadows, lines and
  `color-scheme: dark` so native form controls follow.

### A bug the tests could not have caught

The five swatches rendered as **squares**, not circles. `--r-full` was referenced by four rules
and **declared by none** — and an undefined custom property fails *silently*: the declaration
is dropped, the element simply doesn't get the style, and nothing appears in the console. It
was found by looking at a screenshot, and the machine transcription of that screenshot is what
raised it.

Closed with a general assertion: **every `var(--token)` used in `site.css` or in any page's
markup must be declared** (55 used, with a documented allowlist for the four set at runtime).
This class of failure is now visible to the test suite instead of only to eyes.

## Revolut payments — ported (2026-10-04, second session)

The U4 deferral is now built. The rail is a port of `../fivestarrepairs` (which owns it):
`functions/api/_revolut.js` is copied essentially verbatim, plus the Subscriptions
additions (`createRevolutCustomer`, `createRevolutSubscription`, `getRevolutSubscription`).

**Migration 003** (applied to the live `repeater` DB, each statement separately) adds the
neutral `processor_order_id` / `processor_payment_id` columns to `orders`, the
`idx_orders_processor_order` index, and `revolut_plan_cache`. aphelion migration **029**
was already applied and was verified (`revolut_customer_id`, `revolut_subscription_id`).

**Endpoints** (`functions/api/shop-os/`): `checkout.js` (GET probe, unchanged shape when
unconfigured, plus a POST one-off month), `subscribe.js` (new — the Subscriptions flow),
`webhook.js` (verified → settle). Shapes were checked against the pinned OpenAPI spec
(`merchant-2026-08-17.yaml`), not guessed:

- `POST /api/subscription-plans` (plan + variation created once, cached)
- `POST /api/customers`, `POST /api/subscriptions` → `{ setup_order_id }`
- `GET /api/orders/{id}` → `checkout_url`; `GET /api/subscriptions/{id}` to confirm
- events: `ORDER_COMPLETED`, `SUBSCRIPTION_CANCELLED` (others acked)

**One deviation from the brief, deliberately:** the trial is expressed with the plan's
documented `trial_duration: "P14D"` field, not a zero-amount phase — the spec defines a
trial as a duration, and a zero-amount phase is not a documented shape. `TRIAL_DAYS = 14`
in `_tiers.js` is flagged `[OWNER TO CONFIRM]`.

**A real bug the tests caught:** the migration adds `processor_payment_id NOT NULL DEFAULT
''`, so the webhook's idempotency guard (`WHERE processor_payment_id IS NULL`, ported from
fsr where the column is nullable) matched nothing and **no order would ever have settled**.
It now tests `= '' OR IS NULL`.

Still unverified by design: that Revolut accepts these shapes on Leo's account, and that a
real card settles. See `docs/SETUP-revolut-payments.md` for the runbook.
